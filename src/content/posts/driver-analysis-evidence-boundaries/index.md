游戏目录、系统驱动目录和公共组件目录里，可能同时留着同一产品的多个版本。只根据文件名挑一份来分析，很容易把它的地址和能力套到另一份正在运行的文件上。

近期组件整理的第一步是建立版本身份；地址表的有效期跟随文件身份。

## 磁盘存在与当前加载分开记录

一个样本组里，两份同名基础驱动的文件版本不同，较新的安装目录副本与当时系统实际加载的副本也不同。另一份参考资料中的启动驱动，在该轮本地清点中没有找到。

因此，参考资料的模块名和地址表只能作为历史线索。具体判断需要绑定当时的样本、文件身份和加载记录。组件更新后，应重新建立这层联系。

“没有找到某个文件”描述当次扫描范围，其他安装与机器需要各自扫描。

## API 导入与运行时注册是两层证据

导入表可以说明二进制依赖哪些接口；明确的调用路径与参数构造，才能进一步支持某项注册行为的静态判断。实际是否进入这条路径，还需要运行时证据。

有些 API 名由立即数构造，再经过逐字节变换得到。文件中同时存在的明文 API 字符串，却没有找到预期的直接引用。此时字符串搜索提供导航，调用是否发生由运行时证据回答。

RIP 相对引用的缺失只描述当前扫描范围；间接索引、运行时构造、保护器逻辑和扫描器覆盖范围各自留下缺口。

## 生命周期接口不能直接推出策略

一份报告识别了进程通知、关机通知和崩溃转储相关路径。这些接口分别属于不同生命周期，各自对应独立的判断。

某个回调在可见函数体中只处理进程退出，这描述的是该函数的分支行为；组件是否通过其他路径观察进程创建，需要单独的运行时证据。

关机通知说明组件在该阶段有执行机会，网络上报需要流量或调用证据。崩溃转储回调支持“参与转储构造”的判断，具体收集内容以函数体为准。

## 壳层里的可解码字节仍需辨别

另一组样本存在明文骨架、明显异常的高熵区域、可解码但缺少正常调用关系的指令流，以及放在非预期区域的异常表。

这类结果提示，节名与工具自动函数边界都需要复核：名为 UPX 的节按实际压缩特征判断，能解成指令的数据仍需可达性证据。

熵、指令密度、引用与控制流是互补线索。常见算法常量的缺失描述当前的特征匹配结果；系统密码 API、其他实现和变换后的常量各自需要检查。

## 虚表名字适合导航

用户态配套模块保留了驱动对象、请求管理、数据变换和输入检测相关的 RTTI 与虚表名字。现有离线报告列出了 758 个类型描述符，以及另一轮枚举中的 610 个虚表名称。

这些名字帮助确定下一步看哪些函数；对象是否已在当前进程中构造、能力是否在本轮启用，由运行时证据确认。

## 记录结论时保留层级

对这类组件，比较稳妥的记录方式是分别写清文件存在、静态调用关系、运行时注册、实际触发和外部效果。每往后一层，都需要新的证据。

这次整理保留的是组件结构和分析方法。原始地址、运行参数、凭据与本机路径留在本地研究材料中，博客文章不以它们作为复现入口。
