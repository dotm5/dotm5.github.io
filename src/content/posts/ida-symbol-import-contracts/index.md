把函数入口表和名字表交给 IDA，看起来只是几次创建函数、设置名称的操作。真正容易出错的地方却在输入数据之间：一个文件记录 VA，另一个记录 RVA；一个名字是完整类成员名，另一个只有短方法名。

这些差异通常不会造成解析错误。脚本可以一直运行到末尾，最终数据库却失去刚导入的名字。

## 地址必须带单位

VA 是某个镜像基址下的虚拟地址，RVA 是相对镜像起点的偏移。二者的数值都可能是合法整数，比较之前需要先统一单位。

在这批材料中，入口文件保存基于首选镜像基址的 VA，方法 TSV 第一列保存 RVA。导入脚本也分别使用了相应换算路径。

复核发现，后续“给未命名入口补占位名”的步骤，将入口文件里的 VA 与方法表生成的 RVA 集合直接比较。这个比较把两组不同单位的地址放在一起，本应保护的已命名地址可能因此被重新覆盖。

这是脚本的数据契约问题。归档中没有把它当成已修复项，也没有在原数据库上重跑来试验。

## 名字需要保留所属范围

新的方法表中已经出现真实短名，例如相同名称会出现在多个方法记录里。若把短名直接作为数据库全局唯一名称使用，会碰到重载、跨类同名和共享实现等情况。

一个导入记录应该保留声明类、方法名、成员标识以及代码位置。数据库显示名可以组合这些信息，但原始字段也应保留，方便以后恢复签名或重新消歧。

同一个代码位置对应多个声明时，单一函数名只承载其中一条关系。可以保留一个主名，把其他对应关系记为别名清单或注释。

## 行数和唯一地址数分开统计

本批方法 TSV 有 479,707 行，对应 477,780 个不同 RVA。其中 5,984 行包含非占位方法名。三个数分别回答记录规模、代码位置规模和当前真名覆盖。

较早的静态入口文件有 930,147 行经过序言形状筛选的候选入口。这一数字描述候选数据；真实函数数与 IDA 中成功创建的函数数各自需要测量。

尤其在代码共享、thunk、内联和不规则边界存在时，候选入口需要进一步经过反汇编和数据库结构检查。

## 导入次序需要可检验的保护规则

合理的流程是先统一地址表示，再建立必要的函数，应用有依据的名字，最后处理仍无信息的位置。

每一步都需要输出自己的结果。例如：

| 阶段 | 应单独记录的结果 |
| --- | --- |
| 地址归一化 | 输入单位、目标基址、越界和重复数量 |
| 创建函数 | 成功、已有、位于函数中间、失败 |
| 应用名字 | 成功、重名、已有人工命名而跳过 |
| 填补占位名 | 实际补名数量、已命名地址保护结果 |
| 最终保存 | 保存后的身份与重新打开的抽查结果 |

在离线副本上选少量覆盖同名、重复地址、旧人工名和普通新入口的记录，就能比全量盲跑更早暴露问题。

## 脚本运行结束之后

最终验收应回读名字、函数边界和原型，确认命名没有被最后一轮覆盖。语法检查、文件生成以及打印 `done` 覆盖的是执行状态，回读通过才算落库完成。

研究记录因此把“已经生成导入材料”和“已经导入且保存数据库”分为两项。前者可以交给下一位分析者继续工作，后者则需要实际落库的回执支持。
