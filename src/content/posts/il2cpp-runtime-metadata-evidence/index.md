常规 IL2CPP 工具依赖元数据与原生代码之间的对应关系。两边都能读取时，可以把类型、方法、字段和代码位置组织起来。但在一个受保护的 Windows Unity 样本中，元数据格式已经发生变化，标准工具首先停在文件识别阶段。

这里有两个独立问题：文件能否被工具读取；运行时是否仍存在可识别的对象。文件识别失败之后，运行期结构需要单独调查。

## 磁盘镜像和运行期镜像各自保留什么

早期判断曾把希望放在“运行后会得到完整明文元数据”上。后续对已采集缓冲和磁盘文件做逐字节比较，记录的 102,947,972 字节完全一致。至少在这块缓冲、这个时刻，没有出现预期中的整包明文替换。

原生模块的两份镜像也存在差异：部分代码在运行期被清零，部分区域出现复制或覆盖，另有常规重定位与状态变化。因此，运行期镜像与磁盘文件各自承担自己的内容。静态代码的来源和运行期指针的来源分别保留，再按区域对齐。

这些观察支持的结论是：整块缓冲保持原样，标准元数据需要从运行期结构逐区域恢复。进程内其他位置是否存在别的表示，需要另一次采样。

## 对象图提供了另一种结构

运行期记录中，类型缓存、类对象和方法记录可以通过共同的索引、声明类指针及代码归属互相约束。布局以当前样本标定；公开 Unity 版本的结构体需要逐字段核对后再用。

本次归档有两批需要分开的数据：

| 数据批次 | 记录内容 | 规模 |
| --- | --- | ---: |
| 较早的对象扫描 | 类型缓存记录 | 1,447 |
| 同一批扫描的统计字段 | 类对象 | 80,645 |
| 同一批文件实际保存的带方法类记录 | 类记录 | 29,106 |
| 同一批扫描 | 方法记录 | 478,533 |
| 较晚的 TSV 与符号 JSON | 方法记录行 | 479,707 |

类对象总数与带方法类记录数属于两种口径；两个采样批次的方法数分别统计。后续更新文件时，文章里旧的统计段落不会自动随之更新。

## 方法名恢复经历了一次修正

早期记录写“方法结构里没有名字指针”。后续观察发现，该样本在另一个槽位按需填写名字相关记录。由此恢复出了一部分真实方法名，包括接口实现、编译器生成名和事件访问器。

非空槽位中还包含哈希节点。只有记录形状、字符串内容和所属关系一起符合条件，才能计入真名。

当前较晚一批文件中，479,707 行里有 **5,984 行非占位方法名**，其余 473,723 行仍使用类名与成员序号组成的占位名。这是部分恢复结果，完整方法名表留待后续补证。

同一批 TSV 包含 477,780 个不同代码位置。重复行可能涉及共享实现或其他映射关系；记录行数与唯一函数数分别统计。

## 程序集恢复补上了所属关系

类对象中的一个共享上下文后来被识别为经过字段变换的程序集结构。现有产物包含 81 个程序集记录，声明的类型数量合计 79,294。

程序集声明类型数与运行期类对象数对应不同实体，接近的数值来自各自的口径。恢复程序集所属关系覆盖的是所属关系；命名空间、方法签名和字段类型各自需要证据。

## 当前成果能用在哪里

这批数据已经适合用类名、程序集和部分真方法名缩小搜索范围，再把候选代码位置交给反汇编核对。它支持按名检索和候选定位；生成完整 SDK 还需要字段与签名的进一步恢复。

后续最值得补的验收是：不同采样批次如何合并，重复位置怎样保留多重语义，以及名字导入后是否被后续步骤覆盖。关于导入过程，见[符号导进 IDA 又变回 sub_](/posts/ida-symbol-import-contracts/)；资源文件的处理是另一条路线，见[导出了 11 项资源，算成功吗](/posts/unity-containers-and-asset-validation/)。
