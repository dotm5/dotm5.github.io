找到一个名称里带光照或面部阴影的函数后，渲染分析才刚得到一个入口。要解释画面，还需要知道当前 draw 读了什么、数据从哪里产生，以及原生代码中的设置操作最终落到哪个参数槽。

近期两组 UE 渲染记录分别提供了皮肤延迟光照链和面部阴影对齐的例子。它们属于不同样本，下面分别讨论，两组 GBuffer 布局各自独立。

## 先用像素历史确定哪次绘制有效

皮肤样本的一个目标像素经历了多次相关绘制。其中一次真正改变目标，其他几次被深度测试拒绝。仅按网格外形或事件顺序挑一个 draw，可能选中没有贡献的重绘。

记录中，角色主 pass 写入五张 MRT，场景先在较低分辨率渲染，再合成到更高分辨率的交换链。两个尺寸属于不同阶段；材质计算分辨率与交换链分辨率分别记录。

目标表面绘制时生成的基色、法线与自定义数据属于早期输出。像素历史显示，后续全屏链继续改写场景色，因此需要跟踪写入顺序，才能解释最终肤色的形成。

## 绑定资源比静态贴图清单多一层信息

这份皮肤记录列出 33 个 SRV 绑定，其中包含多张普通贴图和由前置 pass 产生的角色数据 RT。只从资产目录提取基色与法线，会漏掉这些运行期输入。

对这些 RT，可以先确认格式、尺寸、写入者和被哪些 draw 采样。至于它们究竟承载厚度、妆容、光照还是其他数据，需要继续核对 shader 读取方式。

同样，某个收尾 pass 的资源数量与视觉效果接近次表面散射，命名仍需 shader 读取证据。原始记录也将这个语义保留为待验证项。

## 面部 SDF 对齐需要多种证据

另一份角色展示帧先有面部阴影相关的类型、材质槽和资产候选，随后通过 draw 的纹理绑定、资源预览与使用记录，缩小到实际使用的面部掩码。

这里得到的是“当前 draw 使用了与面部阴影语义相符的纹理”。还没有完成的部分，是把具体材质常量逐项对应到角色材质控制器的设置操作。

材质常量块的尺寸差异能提示哪些 draw 使用了不同的数据布局；块内的某组数值命名成面光方向或阴影阈值，还需要写入路径、类型、分量顺序和变换关系的支持。

## 全局参数不一定全部经过 MPC

静态分析早期将一个全局着色参数入口理解成批量写入 MPC。进一步读调用关系后，记录修正为其中还包含动态材质实例的标量、向量和纹理设置。

天气与后处理也要分开追踪。一个更新器可能只是混合设置，真正的参数应用在后续组件或渲染阶段；雾、云、Bloom 和角色调色不必共享同一条通道。

因此，需要分别记录参数生产者、插值或缓存环节、设置器，以及最终材质或渲染组件。函数名称相似，最终写入的 GPU 常量块需要逐项核对。

## 眩光未激活时的记录边界

眩光研究已经找到了相关配置、原生入口与资产名称，但所选帧中没有获得可见眩光贡献。这个结果应限制在当前场景和采样条件内。

它不否定静态路径，也没有把一个零贡献的小 draw 认作眩光。要继续对齐，需要让目标效果在新帧中可见，再用实际资源与参数验证。

## 对齐到哪一层就写到哪一层

| 层级 | 可以确认的联系 | 还需要什么 |
| --- | --- | --- |
| 类型和资产 | 存在配置、设置器、材质与贴图候选 | 当前场景是否使用 |
| 帧内资源 | draw 绑定了资源，资源存在写入与消费关系 | 每个通道的计算语义 |
| 参数值 | 设置值与常量槽能对上 | 单位、坐标变换、缓存与插值 |
| 画面效果 | 固定条件改变参数后，目标贡献随之变化 | 跨帧和不同场景复核 |

目前两组记录中，部分联系已经推进到帧内资源层，参数值级对应仍有缺口。保留这个边界，后续研究才能落成可验证的材质或光照重建；相似画面只作为线索。
